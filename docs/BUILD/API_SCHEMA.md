# API schema

An OpenAPI 3.0 document generated from the live URLconf, so it cannot drift from
the API the way a hand-written document does.

| | |
| --- | --- |
| Schema | `GET /api/schema/` (YAML; `?format=json` for JSON) |
| Browsable docs | `GET /api/schema/ui/` (Swagger UI) |
| Auth | **Required on both.** JWT, like everything else |
| Generated by | [drf-spectacular](https://drf-spectacular.readthedocs.io/) |

## Why it is behind auth

The schema is a complete map of every endpoint, every parameter and every payload
shape in the product. It is not secret — an authenticated customer can read it,
and should be able to — but there is no reason an anonymous caller needs it, and
handing an unauthenticated prober a full API inventory is a gift with no
corresponding benefit. Both routes require a token, and a test pins that.

`/healthz` and `/readyz` are deliberately excluded: they exist for the load
balancer, and listing them invites a client to depend on endpoints covered by no
contract.

## Generating it offline

```bash
docker compose exec web python manage.py spectacular --file schema.yml
docker compose exec web python manage.py spectacular --format openapi-json --file schema.json
```

Useful for generating a client, or for diffing two revisions to see exactly what
an API change did.

## The honest state of it

**198 paths are listed, and most of them have no request or response body
documented.** That is a real limitation, not a rendering quirk, so it is written
down here rather than discovered.

The cause: most views in this codebase are plain `APIView`s that validate with a
serializer instantiated inline in the method body, rather than generic views with
a `serializer_class`. drf-spectacular introspects the class, finds nothing to
introspect, and emits `unable to guess serializer` — 193 of them at the time of
writing. What you get is still genuinely useful: every path, method, path
parameter, and the auth requirement. What you do not get is the shape of what to
send and what comes back.

Fixing it is mechanical and unfinished. The pattern is one decorator per view:

```python
@extend_schema(
    summary="Erase one employee, irreversibly",
    description="Content ABOUT the person is redacted; content they AUTHORED …",
    tags=["Data subject rights"],
    request=EraseUserSerializer,
    responses={200: dict, 403: None, 404: None, 422: None},
)
class UserEraseView(RBACMixin, APIView):
    ...
```

`UserExportView` and `UserEraseView` in `apps/administration/views.py` are
annotated as the worked example — including an `OpenApiExample` for the response
shape, which is the part a client author actually wants. There is a test asserting
they stay annotated, so the example cannot quietly stop being one.

Annotating the remaining views is worth doing per module, when that module is next
touched, rather than as one sweeping change nobody can review.

**These warnings are silenced in `check --deploy`** (`drf_spectacular.W001` and
`W002` in `SILENCED_SYSTEM_CHECKS`). Not to hide them — they are documented right
here — but because 209 of them turned the deploy gate into noise, and `pms.W003`
("this deployment is serving plain HTTP") was buried around line 180 of the
output. A gate nobody reads is not a gate. They remain visible on the command
whose job is the schema:

```bash
docker compose exec web python manage.py spectacular --file schema.yml
```

Un-silence them as the annotation work removes them.

## Two other things the generator reports

**16 `operationId` collisions.** They come from URL pairs like
`/api/goals/` and `/api/goals/{id}` where both `GET`s generate the same name.
drf-spectacular resolves them with numeric suffixes, which is harmless for the
document and slightly ugly in a generated client (`goals_retrieve_2`). Fixed by
naming the operations explicitly in `@extend_schema`, alongside the work above.

**The schema is not versioned yet.** `VERSION` is `1.0.0` and is not bumped
automatically. Once an external consumer exists, that number has to start meaning
something.
