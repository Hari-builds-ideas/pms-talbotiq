# DATA_HANDOVER — demo data vs production data

How mock/demo data is kept **completely separate** from real production data, who
runs what, and the exact commands. Verified against the code (citations below).

## The rule

- **Production boots with an EMPTY database** — schema only. Nothing seeds mock/
  ACME data automatically.
- **`seed_demo_rich` is the ONLY source of mock data**, and it runs **only when a
  human explicitly invokes it** — never on prod boot.
- **Real data enters exclusively through the product**: self-serve signup
  (`POST /api/auth/signup`) creates a tenant + first admin; employees arrive via
  CSV import (`POST /api/admin/users/import`) or invitations.

## What is mock vs real

| | Mock (demo) | Real (production) |
|---|---|---|
| Tenant | `acme` (+ `globex` test fixture) | created by self-serve signup |
| Users / people | seeded by `seed_demo_rich` | signup admin + CSV import + invites |
| Goals / reviews / feedback / recognition / check-ins | seeded | created by real users |
| Password | `Passw0rd!demo` (demo only) | user-set (signup / reset); imported users use SSO or reset |

All mock data is generated by **one script** — `apps/core/management/commands/seed_demo_rich.py`
(+ the cross-tenant fixture `scripts/qa_seed_globex.py`). **No mock data is
hardcoded anywhere else** — verified: no `RunPython`/`loaddata`/`Tenant.objects.create`
in any migration, and no `acme`/`globex` tenant creation in app code outside the
seed/test/QA scripts.

## Deployment team — a clean, empty prod DB

`docker-compose.prod.yml` runs migrations **only** — there is no seed step:

- The one-shot **`migrate`** service: `python manage.py deploy_migrate` (advisory-
  locked; the only place migrations run). `web`, `celery-worker`, `celery-beat`
  all `depends_on: migrate (service_completed_successfully)` and **do not seed**.
- No entrypoint script seeds; no data migration inserts rows.

So a fresh deploy against a fresh managed MySQL comes up with the schema and an
**empty** dataset. The first real tenant is created by a customer hitting `/signup`.

```bash
# Production deploy (empty DB, migrations only):
docker compose -f docker-compose.prod.yml run --rm migrate    # deploy_migrate
docker compose -f docker-compose.prod.yml up -d web celery-worker celery-beat
# → DB has schema, ZERO tenants. Real data arrives via signup + CSV import.
```

**Do NOT run `seed_demo_rich` in production.** It exists for demo/QA only.

## Testing team — seed / reset a demo tenant

```bash
# Seed (or refresh) the rich ACME demo tenant (idempotent):
docker compose exec web python manage.py seed_demo_rich
#   → tenant 'acme', ~211 people, password 'Passw0rd!demo', manager ada@acme.test.
#   → also PURGES any QA-verifier artifacts (see below), so the feed stays clean.

# Cross-tenant isolation fixture (second tenant 'globex'):
docker compose exec -T web python manage.py shell < scripts/qa_seed_globex.py

# One-command full handover test (reseed + smoke + verify + reseed):
./scripts/qa_handover.sh
```

`seed_demo_rich` is **idempotent**: re-running never duplicates rows (named
accounts are reused by email; content uses get-or-create keys). It also **purges
QA-verifier artifacts** at the start of every run — the duplicate "QA kudos"
recognitions, "QA probe" goals/check-ins and "QA JD" drafts that `scripts/qa_verify.py`
creates against the live demo tenant — so repeated QA runs can never accumulate
junk in the demo feed (`_purge_qa_artifacts`, tenant-scoped, QA-markers only).

### Reset a demo tenant hard (optional)

There is no destructive "wipe tenant" command by design (the audit log is
INSERT-only and protects tenant rows). To get a pristine demo, either re-run
`seed_demo_rich` (idempotent refresh + purge) or, for a truly empty environment,
recreate the database volume:

```bash
docker compose down -v && docker compose up -d      # fresh DB, then migrate + seed
```
